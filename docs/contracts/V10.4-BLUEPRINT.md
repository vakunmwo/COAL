# 7. ACOMPANHAMENTOS

Não é outra agenda.

É uma projeção do mesmo `next_action_task_id`.

Grupos:

```text
VENCIDOS
HOJE
PRÓXIMOS
SEM PRÓXIMO PASSO
```

Cada item mostra:
- negócio;
- próximo passo;
- prazo;
- etapa;
- valor potencial;
- responsável.

Ações diretas:
- abrir Venda 360;
- registrar conversa;
- definir novo próximo passo.

Concluir o próximo passo atual:

```text
task.status = done
↓
commercial_case.next_action_task_id = NULL
↓
domain event: commercial_case.no_next_action
↓
Hoje + Acompanhamentos mostram exceção
```

Nunca criar próximo passo fictício automaticamente.

# 10. Diferencial: `Para avançar`

A etapa não é só coluna.

Cada `funnel_stage` possui:

```text
objective
entry criteria
exit criteria
requirements
default next action
sla_days
script
objections
messages
checklist
```

A UI mostra primeiro:

```text
PARA AVANÇAR

✓ contato principal identificado
✓ problema entendido
✓ evidência registrada
! definir próximo passo
```

Gate:
- suave por padrão;
- override exige motivo;
- snapshot do gate fica registrado;
- hard block apenas para transição logicamente inválida.

# 11. Playbook principal — Prospecção COAL UP

## 1. Pesquisa

**Objetivo:** entender o negócio e montar contexto suficiente para investigar.

Requisitos:
- negócio identificado;
- contato ou canal conhecido;
- origem registrada;
- próxima ação criada.

Próxima ação padrão:
`Levantar evidências`.

## 2. Evidência

**Objetivo:** registrar um problema digital demonstrável.

Requisitos:
- pelo menos uma evidência;
- nota contextual;
- próximo passo.

Próxima ação padrão:
`Preparar abordagem`.

## 3. Abordagem

**Objetivo:** iniciar contato real.

Requisitos:
- atividade/conversa registrada;
- contato principal quando disponível;
- próximo passo.

Próxima ação padrão:
`Confirmar interesse e contexto`.

## 4. Diagnóstico

**Objetivo:** confirmar a dor e entender o que precisa ser resolvido.

**DECISÃO DE MODELO:** quando o prospect entra em Diagnóstico com fit confirmado, o mesmo `commercial_case` ganha uma `opportunity`. O Lead não é apagado.

Requisitos:
- contato principal;
- conversa/diagnóstico registrado;
- problema confirmado;
- serviço/linha de solução;
- próximo passo.

Próxima ação padrão:
`Desenhar oferta`.

## 5. Oferta

**Objetivo:** definir solução, escopo inicial e valor comercial.

Requisitos:
- solução registrada;
- valor potencial;
- próximo passo.

Próxima ação padrão:
`Preparar proposta`.

## 6. Proposta

**Objetivo:** colocar uma proposta real em decisão.

Requisitos:
- proposta criada;
- valor;
- estado da proposta;
- data de acompanhamento.

Próxima ação padrão:
`Acompanhar proposta`.

## 7. Decisão

**Objetivo:** registrar a decisão comercial real.

Saídas possíveis:
- ganhou;
- perdeu;
- não agora.

`Perdeu` exige motivo.

`Não agora` exige data ou condição de retorno.

`Ganhou` não significa pagamento recebido.

---

## Regra sobre SLA

Os SLAs das etapas **não foram fixados neste planejamento**.

Motivo:
- ainda não temos histórico observado suficiente para afirmar que, por exemplo, Diagnóstico deve durar X dias;
- o CRM não deve transformar hipótese em fato operacional.

Na primeira implementação:
- a arquitetura suporta `sla_days`;
- a UI pode exibir “referência não calibrada”;
- o valor só entra depois de medição real ou decisão explícita de Jhonatan.

# 17. Segurança por compartilhar o domínio

A sessão administrativa deve ser isolada o máximo possível.

Cookie recomendado:

```text
HttpOnly
Secure
SameSite=Strict
Path=/crm
```

Consequência:
- o site público não precisa receber o cookie do CRM;
- o endpoint público de intake não depende da sessão administrativa.

Outras regras:
- `/crm/` autenticado server-side;
- `/crm/api/` exige sessão + autorização;
- CSRF em mutações privadas;
- rate limit em login;
- `Cache-Control: no-store` no CRM;
- `X-Robots-Tag: noindex, nofollow`;
- CSP própria para CRM;
- nenhuma credencial no JS público.
